## Scope

This slice closes the previously partial `ui.nodes.catalog_and_import` gate for
the following behavior:

- catalog loading and filtering;
- successful custom manifest import through the real backend;
- catalog refresh and browser reload visibility;
- adding the imported node to the workflow editor; and
- single-consumption of the navigation intent used by the Add-to-canvas action.

Workflow templates, provider-backed execution, plugin script execution, and
external integrations were not treated as part of this slice.

## Defect found and fixed

The first full run of the expanded import-placement E2E exposed two identical
custom nodes after one Add-to-canvas click (`expected 1`, `received 2`). The
workflow page could consume the same `location.state.workflow_intent` more than
once before the replacement navigation cleared the state.

`WorkflowPage.tsx` now records a stable key for each `add-node` or
`load-template` intent in a ref and ignores a repeated key until the navigation
state is cleared. The regression passes in both the full spec and repeated
execution runs.

## Cleanup and limitations

The real-server check used the repository default `data/` resource root because
the local settings file did not specify an override. The imported manifest had a
unique validation-only ID and was removed after the browser check; no validation
fixture or generated bytecode was committed. The pre-existing `assets/cache/`
directory was preserved and left unstaged.

This evidence does not change the separate provider-backed execution blocker or
the partial Chat-history gate. The next actionable slice is a focused Tier 2
pass over the remaining graph/compiler/lifecycle behavior, with templates or
external integrations kept separate unless their scope remains small enough to
validate end to end.
